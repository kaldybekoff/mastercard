## Детальный разбор каждого критерия

### 1. ML Solution Quality (25%)

**Что нужно:**
- ✅ Обоснование выбора модели (почему LightGBM, а не другое)
- ✅ Корректное обучение (train/test split на уровне карт, не транзакций)
- ✅ Validation strategy (holdout + synthetic injection test)
- ✅ Сравнение моделей (LogReg baseline → LightGBM → CatBoost)
- ✅ Подбор гиперпараметров (Optuna)

**Наше закрытие:**
- PU-bagging LightGBM как основная с обоснованием
- LogReg baseline для контраста
- CatBoost как challenger
- Optuna tuning (100+ trials)
- Явный holdout split до обучения

---

### 2. Metrics & Results (20%)

**Что нужно:**
- ✅ **Confusion matrix — ОБЯЗАТЕЛЬНО**
- ✅ Корректная интерпретация метрик
- ✅ Выводы подтверждены данными
- ✅ Результаты показывают эффективность

**Наше закрытие:**
- Confusion matrix с объяснением FP/FN (что дороже для бизнеса)
- PR-AUC + ROC-AUC + F1 + Precision@K
- Synthetic Injection Test — количественный recall
- Все метрики на holdout, не на train

**Ключевой момент для жюри:**
Объяснить почему FP (назвать consumer бизнесом → навязчивое предложение) менее критичен чем кажется (soft-touch маркетинг), и как threshold регулирует этот trade-off.

---

### 3. Data Processing & Feature Engineering (15%)

**Что нужно:**
- ✅ Корректная обработка данных
- ✅ Обработка пропусков и выбросов
- ✅ Описание и обоснование фичей
- ✅ Feature engineering связан с бизнес-задачей

**Наше закрытие:**
- ~80 фичей с бизнес-обоснованием каждой (см. FEATURES.md)
- Явная группировка по смыслу (A-J)
- Обработка outliers (cap на 99-м перцентиле сумм)
- Проверка nulls и дубликатов в EDA-ноутбуке
- MCC-классификация на B2B/Consumer/Mixed с обоснованием кодов

---

### 4. Correctness & Functionality (10%)

**Что нужно:**
- ✅ Решение запускается без ошибок
- ✅ Правильное понимание задачи
- ✅ Модель решает поставленную проблему

**Наше закрытие:**
- FINAL_pipeline.ipynb запускается сверху вниз на чистой машине
- Явная проверка: "мы применяем модель к consumer, не к business"
- Финальный output — список consumer-карт с business-score

**Контрольный чек перед сдачей:**
```

[ ] Все пути относительные (data/raw/, не /Users/имя/)

```

### 5. Code Quality & Structure (10%)

**Что нужно:**
- ✅ Чистый читаемый код
- ✅ Понятные названия переменных
- ✅ Комментарии

**Наше закрытие:**
- Весь переиспользуемый код в `src/`
- Комментарии на русском или английском (единообразно)
- Функции с docstrings
- Никаких magic numbers — все константы в `config.py`
- Snake_case везде

**Примеры:**
```python
# ПЛОХО
x = df.groupby('col1').agg({'col2': 'sum'})
r = 0.8

# ХОРОШО
# Агрегируем суммарные траты по каждой карте
card_total_spend = transactions.group_by("card_number").agg(
    pl.col("transaction_amount_kzt").sum().alias("total_spend_kzt")
)
TRAIN_SIZE = 0.8  # 80% business cards на обучение, 20% на holdout
```

### 6. Creativity & Solution Depth (10%)

**Что нужно:**
- ✅ Оригинальность решения
- ✅ Интересные гипотезы и подходы
- ✅ Обоснование бизнес-ценности
- ✅ Нестандартные идеи

**Наши differentiators:**
1. **PU-learning framing** — правильная постановка, не наивная бинарка
2. **Synthetic Injection Test** — уникальная валидация recall
3. **Merchant graph features** — bipartite overlap
4. **ROI-калькулятор** в дашборде с конкретными числами в ₸

6. **Threshold-as-business-decision**: показываем жюри что мы понимаем операционный контекст

## Распределение времени по критериям

```
ML Quality (25%) + Metrics (20%) + Features (15%) = 60% → ТЕХНИКА
Correctness (10%) + Code Quality (10%) = 20% → ИНЖЕНЕРИЯ  
Creativity (10%) + Docs (5%) + Reproducibility (5%) = 20% → ПОЛИРОВКА
```

**Стратегия:** Нельзя выиграть на одной красоте дашборда. Нельзя выиграть только на высоком PR-AUC без бизнес-истории. Нужны обе части.
